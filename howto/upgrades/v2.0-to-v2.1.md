# Adopt Optional Add-ons from v2.0 to v2.1

## Scope

v2.1 adds optional MCP-backed adapters for Jira, Confluence, GitHub Projects,
and GitLab. Setup includes real client configuration and verified MCP access;
copying the template does not install a server, credentials, or synchronization job. Existing v2.0 projects can keep their workflow unchanged.
New projects follow the normal bootstrap and select an add-on only when needed.

The [add-on guide](../../addons/README.md) owns the shared setup lifecycle.
Project-specific decisions belong in the project's existing documentation root.
The [delivery handbook](../../delivery-system.md) and canonical shared workflow
remain in force.

## Selective Adoption

1. Check the working tree and identify the Delivery System version or commit
   previously adopted. Compare it with the chosen upstream v2.1 source; record
   an unknown baseline or unreleased source honestly.
2. Preserve project content, existing integration rules, documentation roots,
   stable task IDs, security and approval rules, role customizations, and explicit
   diagnostic defaults. Do not replace `docs/` or rerun a completed bootstrap.
3. Copy `addons/README.md`, `addons/mcp-setup.md`, `addons/configure_mcp.py`,
   the selected adapter directories, and this adoption
   guide at `howto/upgrades/v2.0-to-v2.1.md` (or adapt the index link to its actual
   location). Remove index entries and deactivation-prompt links for adapters not
   copied. Keep shared helper/setup files for the selected adapter. Existing
   projects need no changes to role adapters or core workflow rules. Optionally merge discovery links
   from the root README and delivery handbook, adapting paths to your project.
4. Read the shared guide and selected instructions, then use the selected
   integration prompt. Resolve the project's target, authority, mapping, access,
   and allowed operations before dependent setup. Existing connections should be
   inspected and adapted rather than duplicated. Configure/authenticate MCP using
   the actual client's format, reload its session, and verify its catalog and
   target access; a preview or manual instructions alone do not complete setup.
5. Write the durable project integration record and conditional routing pointer
   described in the shared guide. Store all operational rules there so they
   survive removal of the optional instructions. Preserve repository authority
   unless an explicit project decision changes it.
6. Before creating tickets, verify update and native parent/child capabilities,
   stable ID prefixes in visible titles, and reciprocal hierarchy read-back.
   Resolve existing incorrect structures with an approved in-place repair, not
   replacement issues. Mark missing operations blocked; preserve the project's
   explicit source-of-truth decisions. Check links and mappings, verify the
   actual tool permissions, and record
   narrowly scoped results. Distinguish local scenario review from authenticated
   tool/API tests. Only perform external writes within existing authorization.
7. Record the adopted version/source and verification limits in the project's
   existing version or overview record. Review and publish local changes only
   through the project's authorized process.

## Acceptance and Removal Checks

- A project that selects no add-on retains its v2.0 workflow and bootstrap gates.
- Selected prompts configure and verify actual MCP access, resolve blocking
  decisions, and preserve existing IDs and rules.
- Ticket/task native hierarchy and stable ID titles are verified; description
  links or Project membership alone are not treated as hierarchy.
- A customized documentation root remains in use; completed project files are
  preserved except for explicitly agreed additions.
- Local and remote objects are mapped by stable IDs; repeated operations do not
  blindly create duplicates or overwrite concurrent edits.
- The durable record contains actual capabilities, source authority, mapping,
  permissions, failures, verification, and teardown steps without secrets.
- Test removal in a disposable copy: remove an unused add-on and clean its index
  entry; then remove all `addons/` files and their discovery links. Core workflow
  and any configured integration's durable rules must still resolve.
- Disabling a connection follows its recorded teardown procedure. Deleting the
  instructions alone does not stop automation or revoke credentials.

## Rollback

If setup fails, retain failure evidence and restore only the reviewed local
setup changes through the project's normal process. Do not reset unrelated
work. Reconcile any external changes already made using recorded remote IDs;
local file rollback cannot undo remote writes. Obtain required authorization
for compensating changes. Stop only automation installed for this integration,
coordinate credential changes with their owner, and preserve remote history.
If adoption is abandoned, remove optional files and links and retain the prior
version record and any remaining active-connection documentation.
